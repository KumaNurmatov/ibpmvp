# Разбор документов по заказам

Кидаете пачку первички — договоры, спецификации, накладные, CMR, платёжки,
банковскую выписку, сводный реестр, фото и скриншоты. Инструмент определяет,
что есть что, разносит по заказам, считает остатки и выдаёт книгу Excel той же
раскладки, что ведётся руками, плюс лист со всем, что требует человека.

## Как запустить

```bash
pip install -r tool/requirements.txt
export ANTHROPIC_API_KEY=sk-ant-...          # ключ нужен только для распознавания

# веб-приложение
uvicorn tool.app:app --reload                # http://127.0.0.1:8000

# то же самое из командной строки
python -m tool.cli ~/Загрузки/заказ-666 -o Заказы.xlsx
```

## Что происходит внутри

```
файлы ──▶ docs.py ──▶ extract.py ──▶ ledger.py ──▶ export_xlsx.py
          страницы    поля по         заказы,       книга той же
          текстом     схеме           проверки,     раскладки
          или сканом  (модель)        расчёты       + лист «проверки»
                                      (Python)
```

**`docs.py`** решает по содержимому, а не по расширению: если в PDF есть
текстовый слой — отдаём текст (дёшево и точно), если скан — рисуем страницы
в PNG 150 dpi. DOCX и XLSX разбираются целиком, включая таблицы; HEIC и
прочая экзотика приводится к PNG.

**`extract.py`** — один вызов модели на документ, структурированный вывод по
схеме. Результат кэшируется по хэшу файла: повторная загрузка того же скана
бесплатна, а расчёты можно переделывать сколько угодно, не распознавая заново.

**`schema.py`** — единственное, что модели разрешено вернуть. Ни остатка, ни
недоплаты в схеме нет: их нельзя извлечь, их можно только посчитать. Модели
прямо запрещено «исправлять» сумму в документе на произведение количества и
цены — именно такие расхождения и надо ловить.

**`ledger.py`** — сведение и вся арифметика, детерминированно и без модели.

**`export_xlsx.py`** — карточка на заказ в 15 строк, формулы на тех же местах,
что в ручной книге, и у каждой формулы записан посчитанный результат (иначе
ячейка выглядит пустой везде, где файл не пересчитывается при открытии).

## Три правила, на которых всё держится

**Считает Python, а не модель.** Модель приносит то, что написано в бумаге.
Суммы, остатки, просрочки и неустойки выводятся кодом — воспроизводимо,
проверяемо тестами и одинаково от запуска к запуску.

**Противоречие не разрешается молча.** Если спецификация говорит одну цену, а
накладная другую, берётся более доверенный источник (`TRUST` в `ledger.py`:
подписанная спецификация важнее листа заказа, накладная важнее CMR, сводный
реестр — последний), но расхождение остаётся видимым замечанием. В таких
местах и прячутся деньги: на заказе 662 ручной реестр показывал сумму отправки
478 080 ₽ при 812 шт по 480 ₽ — пересчёт даёт 389 760 ₽, разница 88 320 ₽.

**У каждого числа есть происхождение.** В книге к ячейке приложено имя файла,
из которого взято значение, в вебе источник подписан под каждым полем.

## Что проверяется автоматически

| Код | Что ловит |
|---|---|
| `shipment_sum_mismatch` | сумма в накладной ≠ отгружено × цену |
| `order_sum_mismatch` | сумма заказа в документе ≠ заказано × цену |
| `prepay_deviation` | аванс не равен оговорённым 50% |
| `overdelivery` / `underdelivery` | отгружено больше или меньше заказа |
| `late_shipment` | просрочка против срока из спецификации, с неустойкой |
| `conflict` | документы противоречат друг другу по одному полю |
| `missing_fields` | нет цены, количества или отгрузки |
| `no_shipping_doc` | отгрузка есть, накладной нет |
| `unrouted` | документ не удалось отнести ни к одному заказу |
| `linked_by_match` | документ без номера договора привязан по совпадениям |

## Как документы попадают в свой заказ

Ключ — номер договора: `666/1-1`, `дог.666/1-1 от 13.04.2026`, `№666` сводятся
к `666`. Платежи из банковской выписки разносятся по номеру договора в
назначении платежа, поэтому одна выписка обслуживает сразу много заказов. Один
и тот же платёж, пришедший и платёжкой, и строкой выписки, не задваивается.

Лист заказа номера договора не несёт — в бумаге его просто нет. Такой документ
привязывается по совпадениям: внутренний номер заказа, количество, цена, дата,
название изделия. Склейка происходит, только когда совпало минимум два признака
и кандидат единственный; иначе документ остаётся отдельно и попадает в
«проверки». Тихо угадать хуже, чем честно не связать.

## Тесты

```bash
python -m pytest tool/tests -q
```

Фикстуры в `tests/fixtures.py` — разбор пяти настоящих документов заказа
Аи 13.04.26/4 (договор 666/1-1), переписанный с самих бумаг вместе с их
несообразностями. Они позволяют прогонять всё, что идёт после распознавания,
не обращаясь к модели и не тратя деньги.

## Чего здесь пока нет

- Распознавание на живой модели не проверялось: в среде, где писался код, не
  было ключа API. Схема, промпт и вызов написаны по документации SDK, но
  точность извлечения на ваших сканах нужно замерить — для этого достаточно
  прогнать папку заказа 666 через CLI и сверить с `tests/fixtures.py`.
- Нет записи обратно в Google Sheets: сейчас выход — файл xlsx.
- Нет накопительной базы: каждый пакет считается сам по себе. Чтобы видеть
  историю по контрагенту, нужно хранилище заказов между загрузками.
- Нет правки распознанного в интерфейсе: исправления вносятся в Excel.
